The rule, as the linter states it

From eslint.config.js — the element model and the load-bearing constraint:

// platform  -> packages/platform  (the bootstrap; may depend on nothing internal)
// db        -> packages/db        (schema/migrations; may depend on platform only)

A subtlety worth checking in review. The config carries an explicit note that a TypeScript-aware resolver is required for these rules to bite — without it the plugin cannot resolve .js→.ts imports and "silently classifies nothing", i.e. the gate passes while enforcing nothing. The resolver is configured against every apps/*/tsconfig.json and packages/*/tsconfig.json. A reviewer should confirm this survives any future build-tool change, because its failure mode is silent.

3.3 The single write path — the rule that keeps the ledger honest

Stock is the most contended resource in a manufacturing ERP and the easiest to corrupt: five modules have a legitimate reason to move it. XELOR resolves this by giving Inventory sole ownership of the stock tables and forcing every other module through one endpoint.

// apps/api/src/modules/inventory/stock.controller.ts
* THE single write path to stock (DECISIONS-V2 §5.6): POST /api/v1/stock/entries.
* Owned by Inventory; Production and every other module post here — nothing writes the
* stock tables directly. Ledger-critical + race-safe inside the service.

The rule is realised as the STOCK_POSTER port. Six modules resolve that token and none of them touches a stock table: sales (dispatch), purchase (goods receipt), production (issue and output), quality (release and rejection), maintenance (spares consumption), and inventory itself (the implementation). The endpoint additionally requires an Idempotency-Key header and rejects the request with a field-level validation error if it is absent — a stock movement is the write you least want duplicated by a retried request.

3.5 What XELOR deliberately does not do

  • It does not decide. XELOR records what people and rules determine. Every recommendation in this product comes from ONYX and is labelled as such.
  • It does not hard-delete. There is not a single @Delete route in the entire API (§8). Masters, financial and statutory rows are retired via is_active, never removed.
  • It does not reach outside the tenant. No XELOR module opens an outbound connection to a customer's system; that is the connector shelf's job and it is unimplemented (§11.4).

5. Multi-tenancy and row-level security

Tenancy is enforced in the database, by a role that cannot bypass it, on every one of the 242 tenant-scoped tables. This is the control a reviewer should test hardest, because every other isolation claim in the product rests on it.

5.1 The two-role model

6. Transaction, consistency and eventing model

The rule that determines whether this system can be trusted with money is a single sentence: ledger-critical writes stay synchronous, in one transaction, and never on the bus. Everything else about the eventing design follows from wanting that to remain true.

6.1 What is synchronous, and what is not

WriteModeReasoning
Stock movementSynchronousPosted through POST /api/v1/stock/entries inside one transaction, race-safe in the service. An eventually-consistent stock balance is a wrong stock balance.
Journal postingSynchronousVia ACCOUNTS_POSTER. A voucher that posts a second later is a voucher that can post in the wrong period.
Document numberingSynchronousInside the caller's transaction (§7), so a failed insert cannot burn a number.
Audit entrySynchronousaudit.appendInTx(tx, …) — the chain link is written in the same transaction as the change it describes, or neither happens.
Cross-module notificationAsynchronousTransactional outbox. The consumer's work is not part of the producer's correctness.
Report rendering, imports, long AI workAsynchronousBullMQ on Valkey.

6.2 The transactional outbox

outbox_event is written in the same transaction as the domain change, so an event can never describe a change that was rolled back, and a committed change can never fail to produce its event. A relay publishes and stamps published_at; attempts records redelivery.

outbox_event(id, tenant_id, name, payload, created_at, published_at, attempts)
  name is versioned: module.entity.verb.v1
  index ix_outbox_unpublished on (tenant_id, created_at)

Delivery is at-least-once. It is turned into an exactly-once effect on the consumer side by event_consumption, a dedup ledger with one row per (consumer, event) and a unique key that makes a redelivery a no-op. The guarantee is stated precisely in the schema comment:

// Consumer-side dedup ledger for the outbox relay (§5.4). One row per (consumer,
// event) actually handled; the unique key turns a redelivery into a no-op, so the
// bus's at-least-once guarantee becomes an exactly-once EFFECT. Append-only.

6.3 Request idempotency

Every mutating endpoint accepts an Idempotency-Key header; the stock endpoint requires one. The record is more careful than a bare key check:

ColumnPurpose
(tenant_id, key) uniqueScopes the key to the tenant, so two tenants cannot collide.
fingerprint char(64)SHA-256 of the request body. A replay with the same key and a different body is a client bug and is rejected, not silently answered from cache.
status, response_status, response_bodyThe saved answer, so a retried request returns the original response rather than re-executing.

ONYX derives its keys deterministically rather than randomly, e.g. fulfil:{missionId}:v{versionNo}:procure:{vendorId}. This is what makes a mission retry (§15) replay the documents already created and raise only the ones that were not — the vendor does not get the order twice.

6.4 The transaction-scoping rule engineers must know

withTenant() opens a transaction and cannot be nested. Any code path that reads through withTenant, then calls a port that opens its own transaction, then writes, must be written as three phases — read tx → port call (its own tx) → write tx. This is not a style preference; nesting produces a runtime failure. It is the single most common way to get an ONYX mission step wrong, because the ports are precisely the things that own their own transactions.

7. Document numbering and statutory constraints

Problem with a uuid fragmentConsequence
A tax invoice number is regulatedCGST Rule 46(b) requires a consecutive serial number, not exceeding sixteen characters, unique for a financial year. A uuid fragment is unique and sixteen characters and is not consecutive — so the series was not compliant. This is the one number in the system where correctness is a legal question rather than a matter of taste.
A document number is read aloudA storekeeper quotes a GRN number over a telephone; a customer quotes an invoice number in an email. GRN-345C75F7FBFA cannot be dictated without spelling it, or checked by eye against a printed challan.
It carries no yearSO-2627-00014 states which financial year's series it belongs to. The uuid form says nothing, so a register cannot be reconciled by reading it.

7.1 How gaplessness is achieved

One counter row per (tenant, doc type, financial year). Allocation is a single UPDATE … RETURNING, which takes a row lock held for the rest of the caller's transaction.

  • Two clerks saving in the same millisecond serialise on that row and receive consecutive numbers.
  • Because the increment is inside the caller's transaction, a document that fails to insert does not burn a number that would then be missing from the series for ever.
  • A sequence would not give this. PostgreSQL sequences are explicitly non-transactional; a rolled-back insert leaves a gap. Gaplessness is the requirement, so the slower design is the correct one.
Deliberate exceptions. CSP (csp_document_series) and EXPENDITURE keep their own equivalent counters rather than sharing the platform table. A reviewer should confirm those two implement the same in-transaction locking discipline — three counters that behave differently is a worse outcome than one that is slightly duplicated.

12.2 Waiting is a real state, not a pause

Step 12 puts the mission in status waiting, stage monitoring, and advance() refuses to move it:

// Waiting is a durable state, not a decorative step on the way to a fabricated
// closure. A supplier/production/quality/dispatch event must wake the mission; an SSE
// loop is not an event and may not advance it merely because the browser stayed open.

Step 13 similarly refuses to write a close row when the downstream gate is not satisfied — because writing a "waiting" close row would mark the step done, and resume is row-based. A person facing the approval has three responses, all of which are terminal states the system handles: approve, try another plan (the refused strategy is scored out of contention and stays in the list, because deleting it would make the next plan look as though it never considered the obvious option), and stop. A rejection fails the mission and commits nothing — verified by counting purchase orders across a rejection: 75 before, 75 after.

13. ONYX's decision engine — determinism

The governing sentence is "AI explains, never decides." In this build it is stronger than that: for the fulfilment mission, AI does not even explain in the sense of generating text — the engine is deterministic arithmetic, and the only method a language model could own is isolated behind a single interface method that is not currently model-backed.

13.1 The engine interface

export interface IntelligenceEngine {
  readonly name: string;
  readonly kind: "deterministic" | "model";    // declared, and shown on screen

  assess(evidence)              // what is true right now
  recommend(evidence, refused?) // compare the ways through and pick one
  verify(chosen, evidence)      // re-derive. The proposer never grades itself.
  explain(request)               // "This method — and only this one — a model could own."
  confidence(chosen)            // how sure, and why
}

The shipped implementation is DeterministicEngine. No file under packages/platform/src/intelligence/ contains an outbound HTTP call, an SDK import, or an API key reference. There is no network dependency in the decision path, which is why the demo runs fully offline and why the same evidence produces the same plan on any machine.

13.4 And where a model is used, it is a different subsystem

The AI Operations module (ONYX, 33 routes, 17 tables) governs a provider-agnostic router with a closed feature registry, prompt lifecycle, cost ledger, PII egress control and a kill switch. Two CI gates apply:

  • The F1 gate (pnpm eval general.master_dedup) grades the detector — does it find the duplicates.
  • The grounding gate (ai-grounding.ts) grades the explanation. It exists because a local 3B model was measured inventing an identifier and reversing a conclusion. This is the correct shape for AI governance. The code decides; the model is permitted to phrase; and a gate checks the phrasing against the evidence and fails the build. Both gates run in CI job 1 under pnpm ai:eval, against whatever AI_PROVIDER is configured — stub (offline) or ollama (local).

14.4 The PromptPack contract — the model phrases, it never concludes

A provider does not know how to prompt for a feature; the feature contributes that, and — critically — contributes the validator too.

export interface PromptPack<I, O> {
  system: string;              // "Keep it narrow — the model phrases, it never concludes."
  buildUser(input: I): string;
  parse(text: string, input: I): O;
  // MUST throw if the text is ungrounded or malformed —
  // the provider then degrades to the deterministic answer.
}

Three consequences follow, and they are the whole safety story:

  • A feature with no PromptPack never reaches a model at all. OllamaProvider returns the deterministic answer marked degraded: "no_prompt_pack" — so the log shows AI did not really run. A feature is opted in to live inference, never opted out.
  • An ungrounded reply is discarded, not shown. parse() throwing means "the model said something we will not show a user", and the call falls through to the deterministic answer.
  • The ERP never blocks on a model. Unreachable, slow, HTTP error, malformed reply — every path degrades. There is no code path in which a model being down stops a factory from working.

14.9 The costs of this choice, stated

  • A 3B local model is materially weaker than a frontier hosted model. The grounding gate exists precisely because of what that weakness produced. Features whose value depends on strong reasoning are marked stretch, not committed.
  • Local inference needs local hardware. The per-plant hardware requirement, and who pays for it, is a commercial question this document does not settle.
  • No hosted provider has been exercised end to end. The router is provider-agnostic by construction and by interface, but that claim has not been proved by actually binding a hosted provider and running the gates against it. Tracked as R-11 in §18.
  • The AI module is not what the fulfilment demo runs on. Missions are decided by the deterministic engine (§13). A reviewer impressed by the mission arc should not attribute it to a model, and this document should not let them.

15. Failure, retry and recovery

15.1 A failed step stops the mission and says so

Scenario 8 exists to demonstrate this and is the only demo scenario designed to fail. Its recorded reason is written to be indistinguishable in shape from a real refusal:

status: failed · stage: execution · steps: 10
waitingReason: "purchase order creation/verification failed — Simulated fault, armed by
demo scenario 8 — PURCHASE was never called. A real refusal here would read exactly like
this: the vendor is on a credit hold that only a person can lift."

15.2 Retry replays rather than duplicates

POST /fulfilment/missions/:id/retry re-runs the last failed step. It is safe for a stated reason: every execute step derives its idempotency key from the mission, the plan version and the vendor — and from nothing that varies between attempts. So a re-run replays the documents that already exist and raises only the ones that do not. The vendor does not get the order twice.

And the failure is not swallowed. The failed step row must be removed, because the arc's resume point is a row count and a failed row would make the mission think that step was done. Before it goes, the failure is written to the event log and the hash-chained audit trail, and the re-run opens with a retrying row carrying the reason the first attempt failed. The code comment states the stakes exactly: "A retry that quietly produced a clean-looking mission would be the most dangerous feature in this product."

18. Gap, risk and decision register

Eleven open items. Each states the condition, the actual consequence, and what would close it. Nothing here is hypothetical — every item was observed on this build.

IDSeverityConditionConsequenceWhat closes it
R-1HIGH Public-demo bypass: a static header is a signed-in administrator when API_PUBLIC_DEMO=true. No secret, no expiry, no revocation. Mitigated by the tenant pin to the two demo ids and by NOT_A_DEMO_DATABASE on reset — but the flag reaching a real-data environment is a configuration mistake away. Make the guard structural: refuse to boot with API_PUBLIC_DEMO=true if the database contains any tenant outside the demo set, rather than checking only at reset time.
R-2MED 9 of 257 RLS policies omit the NULLIF guard (all six fulfilment_*, both data_import_*, quality_release). Not an isolation defect — all fail closed. With the GUC set to empty string they raise invalid input syntax for type uuid: "" instead of returning zero rows, surfacing as a 500 and putting a Postgres error in the log. One migration rewriting the nine predicates to the guarded form; extend rls-check to assert policy shape, not just presence.
R-3MED List envelopes are not uniform: some endpoints return {items:[…]}, others {data:[…]}. Any client written against one shape silently reads undefined from the other. Cost several hours of integration debugging during this review alone. Pick one, migrate the minority, and add a contract test that fails on a list response using the other key.
R-4HIGH No performance testing at scale. RLS overhead measured only at 6,208 rows. The binding decision "RLS overhead >15–20% triggers a design review" is currently untestable — the criterion exists but has never been evaluated under conditions where it could fail. Composite-index-leads-with-tenant_id discipline is likewise unvalidated at volume. A seeded volume dataset (≥10⁶ rows on the hot tables), a load profile, and the RLS comparison re-run against it.
R-5MED 12 of 39 e2e tests are environment-skipped in the public-demo configuration. Sign-in, persona isolation and credential rejection are never exercised in the configuration that is most often run. A regression in the Keycloak path would not be caught by a green suite. A second CI matrix leg that runs the suite with Keycloak enabled and API_PUBLIC_DEMO=false.
R-6LOW Demo scenario 5 (missing-information) cannot start. The resolver honestly reports that no seeded order lacks a released BOM or a qualified supplier, so 1 of 9 scenarios shows UNAVAILABLE in the picker. The refusal behaviour it demonstrates is therefore never shown. Seed one confirmed order whose finished good has no active BOM, or one shortage with no qualified supplier.
R-7LOW demo/reset clears missions but retains the purchase and work orders they raised. Deliberate — they are real ERP documents and "a demo convenience is not a reason to make them erasable". But document numbers climb and stock depletes across repeated reruns, which can eventually flip scenarios to UNAVAILABLE mid-presentation. Presenter guidance, or a separate full-world rebuild (pnpm demo:rebuild) between sessions.
R-8LOW The mission's step-by-step pipeline visual is present on 4 of the 10 module screens the tour visits, plus Mission Control. On the other 6 screens the Trigger→Collect→…→Record breakdown is not shown, so the "show the pipeline everywhere" requirement is partially met. Mount the stage panel on the remaining screens, or return the rail to the shell-level copilot.
R-9LOW The copilot card attributes every step to ONYX. The arc assigns steps to AXLE, SPAR, KILN and HEXA (§12), so the card's "ONYX used…" sentence disagrees with the step's own agentKey on 8 of 13 steps. Render current.agentKey and its role rather than a constant.
R-11MED Provider-agnosticism of the AI router is proved by interface, not by exercise. No hosted provider has ever been bound and run through the router, the governance gates, the budget ledger and the two CI eval gates. The abstraction is clean and the seam is one line — but "it will swap cleanly" is currently a design claim, and token accounting, latency behaviour and error mapping for a hosted provider are all untested. Bind one hosted provider behind a feature flag, run pnpm ai:eval against it, and keep it as a second CI matrix leg.
R-10MED Mobile/offline-first strategy is undecided. Named in the governance document as the largest open gap and a blocking gate before the UX freeze and the manufacturing auth pack. A shop floor is the one place a browser session cannot be assumed. An ADR reviewed by HEXA, before the UX freeze rather than after.

19.1 The summary a reviewer can rely on

What this build genuinely demonstrates

  • Database-enforced multi-tenancy on 242/242 tables, with a non-bypassing application role.
  • Mechanically enforced module boundaries — 24 modules, zero cross-module imports, checked in CI.
  • A tamper-evident audit chain protected by two independent mechanisms, both demonstrable.
  • An intelligence layer that reaches the ERP only through 15 declared ports and writes real, verifiable documents.
  • A deterministic decision engine with no network dependency, an independent critic, and authority expressed as configuration.
  • An AI module that is honest about itself: a closed 10-entry registry, local-or-no model, fail-closed governance, a hash-chained call log, and every feature required to beat a named rules-only baseline.
  • 995 automated tests and five structural proof gates, all currently green.

What it does not yet demonstrate

  • Any behaviour at production scale — no load test, no concurrency test, RLS overhead unmeasured where it could fail.
  • A safe authentication story for the demo configuration (R-1).
  • A single live connector to any external ERP — all eight are declared and none is implemented.
  • Sign-in and persona isolation under CI, which the current configuration skips (R-5).
  • Mobile or offline operation, which is undecided (R-10).
  • A hosted AI provider exercised end to end — the router is provider-agnostic by construction but has only ever run a local model or the offline stub (R-11).
  • Autonomous external execution. The product does not claim it, and the code does not do it.
The single sentence to take away. XELOR's architecture is stronger than its operational evidence: the structural controls — tenancy, boundaries, audit, ports, determinism — are enforced by machines rather than asserted by documents, and each was re-proved while writing this dossier. What is missing is not design; it is scale evidence and the closing of a small, named set of gaps, every one of which is listed in §18 with the work that would close it.
